# PowerPoint Build Guide — 25-Slide Mini Digital Collection

Use this document while building the actual PowerPoint. Follow the slide order exactly so the presentation matches the reference structure. The companion [slide content guide](./SLIDE_CONTENT_GUIDE.md) contains full speaker notes; this document focuses on **what to place on each slide, what work/evidence to prepare, and how to arrange the text, images, and diagrams**.

There are exactly 25 main slides and 10 presenters. Do not remove slides to match the presenter count.

## Overall visual order and style

- Use a consistent school/library colour palette, font pair, footer, and page number.
- Keep each slide to one main idea. Use the short text below on screen; explain details verbally.
- Use real collection examples only when verified and cleared for presentation. Mark a mock-up as **Example**.
- Replace all square-bracket prompts with verified facts. If a fact is not known, say **Unknown** or **Not yet completed** rather than guessing.
- Use the suggested diagrams as simple PowerPoint shapes; avoid decorative complexity.
- Put sources and image credits in the footer or references on Slide 25.

## Presenter-to-slide order

| Presenter | Slides | Main responsibility |
|---|---:|---|
| 1 | 1–3 | Cover, group members, assignment question |
| 2 | 4–6 | Project title, introduction, importance |
| 3 | 7–9 | LMS access, objectives, scope |
| 4 | 10–12 | Selection, value, rights |
| 5 | 13–15 | Workflow, preparation, capture |
| 6 | 16–17 | Image work, OCR, QC, naming |
| 7 | 18–19 | Metadata approach and required elements |
| 8 | 20–21 | Example record and LMS metadata |
| 9 | 22–23 | Masters, storage, backup, access |
| 10 | 24–25 | LMS limitations and conclusion |

## Slide-by-slide build order

### Slide 1 — Institutional title

**Text, top to bottom**

1. `KAMULI CHURCH OF UGANDA PRIMARY SCHOOL`
2. `Kamuli CU Library`
3. `Library Automation and Digitization`
4. `Group 2 — Mini Digital Collection`
5. `[Course/class] · [Presentation date]`

**Layout/visual:** Center the school and project title. Place the school badge or one approved collection image as a modest visual; leave plenty of clear space.

**Prepare:** Confirm the official school/library wording, course, date, and image permission.

**Do not:** Add an extra cover slide before this one; this is Slide 1 of the 25.

### Slide 2 — Group members

**Text:** Heading `GROUP 2`; list the names of the **10 actual members**.

**Layout/visual:** Two balanced columns of five names. If student numbers are required, add them consistently; otherwise omit them.

**Prepare:** Verify the spelling and order of all names with the group.

**Do not:** Leave 11th or 12th placeholder names.

### Slide 3 — Assignment question

**Text**

> **Group 2 — Build a Mini Digital Collection**
> - Select approximately 10–15 digital objects.
> - Assess rights before digitization and sharing.
> - Explain selection criteria and collection value.
> - Complete and describe the digitization workflow.
> - Create Dublin Core metadata for each object.
> - Explain storage, preservation, backup, and access.

**Layout/diagram:** Put the assignment heading above six short requirement tiles/icons. Add a small footer: `Based on the Group 2 assignment brief`.

**Prepare:** Check that the summary preserves the assignment's wording and key requirements.

### Slide 4 — Project title

**Text**

> `BUILDING A MINI DIGITAL COLLECTION`
> `[Your collection title]`
> `A Group 2 digitization exercise using Kamuli CU Library's Digital Archive`

**Layout/visual:** Large title on the left; one cleared collection image or a neutral illustration on the right.

**Prepare:** Select the real collection title. If no collection item is approved for display, use a neutral image and label any sample as a demonstration.

### Slide 5 — Introduction

**Text**

> `A digital collection is more than a folder of scanned files.`
> `Select → assess rights → digitize → describe → preserve → provide access`

**Diagram order**

```text
[Source materials] → [Digital objects] → [Organized collection] → [Discovery]
```

**Layout/visual:** Use one horizontal arrow diagram across the center. Put one short explanatory sentence below it.

**Prepare:** Agree on the simple definition and make sure the steps match the assignment.

### Slide 6 — Importance of a mini digital collection

**Text**

> `Preserves and documents local or institutional history`
> `Makes approved materials easier to discover`
> `Supports teaching, learning, and research`
> `Connects objects to useful descriptions`

**Layout/diagram:** Four benefit tiles in a 2-by-2 grid with simple icons. Add a small callout: `Value to our group/community: [verified or intended value]`.

**Prepare:** Choose benefits relevant to the actual collection. Do not add unsupported statistics or claim proven impact.

### Slide 7 — Importance continued: LMS access

**Text**

> `Kamuli CU Library: https://kamuli-cu.vercel.app`
> `Digital Archive: https://kamuli-cu.vercel.app/digital-collections`
> `Approved public objects can be searched, previewed, and downloaded.`

**Layout/visual:** Put the two links in a side panel. Show one screenshot of the public Digital Archive, if available and safe.

**Prepare:** Test the links and capture a backup screenshot. Use public, approved material only.

**Do not:** Suggest the website performs scanning or provides preservation backup.

### Slide 8 — Assignment objectives

**Text**

> 1. Visit a library/records centre with digitization services.
> 2. Build a mini collection of approximately 10–15 objects.
> 3. Assess rights and explain selection decisions.
> 4. Complete and quality-check the digitization workflow.
> 5. Create Dublin Core metadata for every object.
> 6. Explain storage, backup, preservation, and access.

**Layout/diagram:** Arrange the six objectives as a numbered vertical list or six compact steps; highlight the current project stages only if status is verified.

**Prepare:** Mark actual status as complete, in progress, or planned; avoid implying that every task is complete.

### Slide 9 — Collection scope and overview

**Text**

> `Collection: [Title]`
> `Topic: [Subject]`
> `Date range: [Verified dates or Unknown]`
> `Source: [Approved source description]`
> `Current object count: [Actual number] · Target: approximately 10–15`

**Layout/visual:** Use a scope card beside a small contact sheet of approved objects.

**Prepare:** Verify title, scope, source description, date range, and current count. Exclude restricted/pending objects from the contact sheet.

### Slide 10 — Selection criteria

**Text**

> `Relevant to the collection topic`
> `Known source or provenance`
> `Permission to digitize`
> `Can be described accurately`
> `Suitable for the intended access level`

**Diagram**

```text
[Candidate materials] → [Apply criteria] → [Selected objects]
                                  ↘ [Exclude / hold for review]
```

**Layout/visual:** Draw the selection funnel using three boxes and a side branch for excluded/pending material.

**Prepare:** Match criteria to the group's real decisions. Choose one real included and, if applicable, one excluded example for the speaker.

### Slide 11 — Collection value and materials

**Text**

> `Materials: [Actual material types]`
> `Why included: [Reason]`
> `Audience: [Who may use the collection]`
> `Potential use: [Learning/research/local history]`

**Layout/diagram:** Use a three-step chain: `[Materials] → [Information preserved] → [Potential users/use]`.

**Prepare:** Select 2–4 material types and support the value statement with a specific rationale.

### Slide 12 — Copyright, rights, and privacy

**Text/table**

| Assessment | Decision |
|---|---|
| Permission/public-domain basis verified | Use within documented terms |
| Restricted or sensitive | Do not provide public access |
| Unclear or pending | Hold back and seek advice |

**Layout/visual:** Put the table on the left and three small status symbols (check, lock, question) on the right.

**Prepare:** Complete an item-level register with source, rights decision, evidence reference, reviewer, and access decision. Keep confidential evidence off the slide.

### Slide 13 — Complete workflow at a glance

**Text/diagram**

```text
Prepare → Capture → Correct → OCR (if suitable) → Quality-check
       → Name → Describe with metadata → Store → Controlled access
```

Add a small legend: `Completed · In progress · Planned` and indicate status only where supported by evidence.

**Layout/visual:** Use a single horizontal process line; split into two rows if needed for readability.

**Prepare:** Agree which steps are actually completed, pending, or not suitable for your objects.

### Slide 14 — Prepare and organize source materials

**Text**

> `Confirm permission and restrictions`
> `Identify each object and record its source`
> `Check condition and handling needs`
> `Arrange objects in a consistent capture order`

**Layout/visual:** Four numbered preparation cards or a checklist next to a permitted preparation photo.

**Prepare:** Have actual preparation notes and an object-to-source link. Do not show restricted originals.

### Slide 15 — Scan or photograph

**Text**

> `Capture method: [Scanner/camera]`
> `Settings: [Recorded settings, if known]`
> `Objects captured: [Actual count]`
> `Capture date: [Date]`

**Layout/visual:** Use a simple `Original → Scanner/camera → Digital capture file` diagram. Place the capture details beneath it.

**Prepare:** Record device/method, settings if available, capture date, and count. Use a permission-cleared equipment photograph if possible.

**Do not:** Claim the LMS did the capture.

### Slide 16 — Image correction and OCR

**Text**

> `Image work: [Actual crop/rotation/correction or not completed]`
> `OCR: [Tool/language, not suitable, or not completed]`
> `Text objects processed: [Actual count]`

**Layout/visual:** Two side-by-side panels labelled `Image processing` and `OCR`. Show a before/after or OCR sample only if it is real and safe.

**Prepare:** Identify which copy was modified, which tool was used, and the actual OCR status. Preserve an unchanged master if that is your group's method.

### Slide 17 — Quality control and file naming

**Text**

> `Image checks: orientation · focus · completeness · readability`
> `OCR check: [Actual method/status]`
> `Naming pattern: [collection]_[identifier]_[type]_[version]_[role].[extension]`
> `Example: [Actual filename]`

**Layout/diagram:** Show a checklist beside one filename, with arrows or colour blocks identifying each filename component.

**Prepare:** Use actual filenames and QC results. Label example names as examples if they have not been applied.

### Slide 18 — Metadata approach

**Text**

> `Metadata helps answer:`
> `What is it? Who created it? When? What is it about? How is it identified?`
> `Create one complete record for every object.`

**Diagram**

```text
[Digital object] ── linked to ── [Metadata record]
                                      ├─ title/creator
                                      ├─ subject/description
                                      └─ identifier/format
```

**Prepare:** Select a safe example object and connect it to its actual record.

### Slide 19 — Dublin Core elements required

**Text/table**

| Element | Meaning |
|---|---|
| Title | Object name |
| Creator | Person/organization responsible |
| Date | Creation/documented date |
| Subject | Topics or keywords |
| Description | Factual summary |
| Type | DCMI type term |
| Format | File format/MIME type |
| Identifier | Unique object ID |
| Language | Language, where applicable |

**Layout:** Use a two-column table; fit the text at a readable size. If necessary, shorten meanings without removing required elements.

**Prepare:** Verify the terms against the assignment and Dublin Core reference.

### Slide 20 — Example Dublin Core record

**Text/table:** Show one complete real record only: Title, Creator, Date, Subject, Description, Type, Format, Identifier, Language. Use `Unknown` or a documented estimate where appropriate.

**Layout/visual:** Present it as a metadata card: field names in a narrow left column, verified values in a wider right column.

**Prepare:** Confirm every value against a source. Use an approved object; conceal personal or restricted details.

**Do not:** Present template values as if they were collected facts.

### Slide 21 — Dublin Core in the LMS

**Text/diagram**

```text
[Staff upload/edit form] → [Saved object record] → [Public display if approved]
                                      └──────────→ [Staff CSV export]
```

Add a short note: `Staff enter descriptive values; the system assigns Identifier and derives Format from the uploaded MIME type.`

**Layout/visual:** Prefer 2–3 screenshots with arrows. Otherwise recreate the process as a clean diagram.

**Prepare:** Capture screens using a test or approved record. Hide login details, emails, and sensitive rights notes.

### Slide 22 — Preservation masters and access copies

**Text/table**

| File role | Purpose | Our example/location |
|---|---|---|
| Master | Retained preservation version | [Actual/planned] |
| Access copy | Convenient version for delivery | [Actual/planned] |

**Diagram**

```text
[One object / identifier]
        ├── [Master file: retained, unchanged]
        └── [Access copy: viewing/delivery]
```

**Prepare:** Identify actual file formats, locations, and roles. If your project has not made masters/access copies, label the arrangement planned.

### Slide 23 — Storage, backup, preservation, and access

**Text/table**

| Need | Arrangement/status |
|---|---|
| Working files | [Location/responsible person] |
| Masters | [Stable restricted location] |
| Backup | [Separate location/restore-check status] |
| Access copies | [Public/controlled delivery] |
| Review | [Check schedule] |

**Diagram**

```text
[Master storage] → [Separate backup] → [Restore check]
[Access copy]    → [Public or controlled access]
```

**Prepare:** Distinguish completed, planned, and unverified arrangements. Never call a backup verified until a restore/check was actually performed.

### Slide 24 — System features and limitations

**Text/table**

| LMS supports | Group work / not implemented in LMS |
|---|---|
| Collections and uploads | Visit and source preparation |
| Rights notes and public/private controls | Scanning and image correction |
| Dublin Core entry and CSV export | OCR and image/OCR quality checks |
| Public search, preview, download | Preservation master workflow and verified backups |

Footer: `QR generation/scanning is not implemented and is not required by the supplied assignment.`

**Layout:** Two contrasting columns with equal visual weight.

**Prepare:** Check claims against the actual LMS and keep the difference between system capability and assignment work clear.

### Slide 25 — Conclusion and references

**Text**

> `Our collection: [Title] · [actual number] objects`
> `Key learning: [Main result or lesson]`
> `Next step: [One realistic action]`
> `Thank you — Questions?`

**References/credits:** Group 2 assignment brief; [Dublin Core terms](https://www.dublincore.org/specifications/dublin-core/dcmi-terms/); [Digital Archive](https://kamuli-cu.vercel.app/digital-collections); image credits/licenses.

**Layout/visual:** Conclude with one approved collection image or a small end-to-end diagram: `[Source] → [Described digital object] → [Appropriate access]`.

**Prepare:** Confirm all claims, links, and credits; finish with the group's actual takeaway and next action.
